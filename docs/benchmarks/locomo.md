## Description

LoCoMo evaluates whether LLM agents can answer questions correctly over very long, multi-session
dialogues. Per the paper's own abstract (ACL Anthology): the authors "introduce a machine-human
pipeline to generate high-quality, very long-term dialogues by leveraging LLM-based agent
architectures and grounding their dialogues on personas and temporal event graphs," and "equip
each agent with the capability of sharing and reacting to images." The generated conversations
"are verified and edited by human annotators for long-range consistency and grounding to the
event graphs."

Section 3 ("Generative Pipeline for LoCoMo", per the arXiv/ar5iv text) describes the same
pipeline in more detail: "unique persona statements p are assigned to each agent," a "temporal
event graph 𝒢" is created "for each agent, which illustrates a realistic sequence of life
events," and human annotators are tasked with "(1) editing the dialogue to eliminate long-term
inconsistencies, (2) removing or substituting irrelevant images."

The dataset's own `README.MD` states each conversation is "annotated for the question-answering
and event-summarization tasks," and that "the dialogs in each conversation can be used for the
multimodal-dialog-generation task." **This page covers only the question-answering task.**

**Images**: this is a point of discrepancy between two official sources. Section 5
("Experimental Setup", per arXiv/ar5iv) states that for the QA and event-summarization tasks,
"we replace images in LoCoMo with their captions generated using BLIP-2" — i.e., raw images are
only used directly in the multimodal dialogue-generation task, not in QA. The repo's own
`README.MD`, however, describes the dataset's `blip_caption` field as "caption generated by the
[BLIP](https://huggingface.co/Salesforce/blip-image-captioning-large) model" — linking to the
original BLIP model (`Salesforce/blip-image-captioning-large`), not BLIP-2. Both are official
sources (the paper text and the repo's own field documentation) and they name different model
versions; this is flagged under Open questions below rather than silently resolved.

## Task format

QA over the full multi-session conversation history. Each item has `question`, `answer`,
`category` (integer 1–5), and `evidence` — "a list of dialog ids that contain the answer, when
available" (quoted from the repo's `README.MD`). §4.1 of the paper defines five question
categories, in this prose order: "(1) Single-hop questions require answers based on a single
session; (2) Multi-hop questions require synthesizing information from multiple different
sessions; (3) Temporal reasoning questions can be answered through temporal reasoning and
capturing time-related data cues within the conversation; (4) Open-domain knowledge questions can
be answered by integrating a speaker's provided information with external knowledge such as
commonsense or world facts; (5) Adversarial questions are designed to trick the agent into
providing wrong answers."

**The paper's prose order above does not match the dataset's actual `category` field values.**
This page originally assumed category 1 = single-hop by following the prose order, and was
wrong. Two independent pieces of evidence from the official eval code confirm the true mapping:

1. `task_eval/evaluation_stats.py` reports per-category results in the fixed order
   `keys = [4, 1, 2, 3, 5]` — i.e., remapped to the paper's single-hop/multi-hop/temporal/
   open-domain/adversarial table order — and separately computes a farthest-to-latest
   evidence-session span only for `qa['category'] == 1`, a metric that only makes sense for
   multi-hop questions (spanning sessions).
2. `task_eval/evaluation.py`, function `eval_question_answering`, contains these verbatim code
   comments directly above the per-category branching logic: `# single-hop, temporal, open-domain
   eval without splitting for sub-answers` guarding `if line['category'] in [2, 3, 4]`, and
   `# multi-hop eval by splitting entire phrase into sub-answers and computing partial F1 for
   each` guarding `elif line['category'] in [1]`.

Combined, these give the mapping:

| JSON `category` value | Actual meaning |
|---|---|
| 1 | Multi-hop |
| 2 | Temporal reasoning |
| 3 | Open-domain knowledge |
| 4 | Single-hop |
| 5 | Adversarial |

This is further corroborated by evidence-pointer statistics across all 10 released
conversations (1,986 QA pairs): category 1 has multi-session evidence in 95.4% of items
(multi-hop signature), category 4 in 0.2% (single-hop signature), category 2 items are
near-uniformly "when did X happen" questions with single-session evidence (temporal signature),
category 5 items carry a distinct `adversarial_answer` field paired with `answer: null`
(adversarial signature), and category counts in this subset (14.2%/16.2%/4.8%/42.3%/22.5% for
1/2/3/4/5) track the paper's Table 5 percentages for multi-hop/temporal/open-domain/single-hop/
adversarial respectively far better than the originally-assumed order.

**Minor technical note**: `evaluation.py`'s `eval_question_answering` also special-cases
category 3 — `if line['category'] == 3: answer = answer.split(';')[0].strip()` — taking only
the first of possibly several semicolon-separated candidate answers before scoring.

## Metric

The metric is **not uniform across categories** — this is confirmed directly from
`task_eval/evaluation.py`, function `eval_question_answering`, not merely from the paper's prose:

- **Categories 2, 3, 4** (temporal, open-domain, single-hop): scored with `f1_score`, a
  token-level F1 over Porter-stemmed, normalized tokens (articles/punctuation/case stripped) —
  standard single-answer F1.
- **Category 1** (multi-hop): scored with `f1`, which splits both the prediction and the gold
  answer on commas into sub-answers, then averages, for each gold sub-answer, the maximum
  `f1_score` against any predicted sub-answer. This is a distinct multi-answer partial-credit
  metric, not the same computation used for categories 2–4.
- **Category 5** (adversarial): scored by exact substring check, not F1 at all — the prediction
  is correct (`1`) only if it contains the phrase `"no information available"` or `"not
  mentioned"` (case-insensitive), and incorrect (`0`) otherwise.

The paper's own description (§4.1, via ar5iv) states: "we calculate the F1 score for exact
matches, following the normalization of both the predicted and the actual ground truth
answers," and separately, "we employ the F1 partial match metric for evaluating the
predictions" — consistent with the F1-based categories above, though the paper prose does not
call out that category 5 uses a wholly different, non-F1 pass/fail check; that detail is only
visible in the eval code itself.

**Metric-blending caveat**: because category 5 is scored as a binary 0/1 phrase-match while
categories 1–4 are scored as continuous F1, any "overall" score that averages across all five
categories is blending two different measurement types, not just aggregating one consistent
metric. This also means a system that correctly abstains but phrases it differently (e.g. "I
don't know" or "the conversation doesn't say") would score 0 on an adversarial item despite
correctly recognizing it as unanswerable — a specific, code-verified metric blind spot relevant
to future scoring of [Capability 10, Memory Calibration](../capabilities/10-memory-calibration.md).

## Sample data

Reproduced from `data/locomo10.json` (sample `conv-26`) under the dataset's CC BY-NC 4.0
license (attribution: LoCoMo, Maharana et al., ACL 2024 / arXiv 2402.17753).

**Single-hop (`category: 4`)**:

```json
{
  "question": "What did the charity race raise awareness for?",
  "answer": "mental health",
  "category": 4,
  "evidence": ["D2:2"]
}
```

`evidence: ["D2:2"]` points to one turn — Caroline: *"That charity race sounds great, Mel!
Making a difference & raising awareness for mental health is super rewarding..."* — which alone
fully answers the question, consistent with the
[Direct Retrieval definition](../capabilities/01-direct-retrieval.md) (Capability 1).

**Multi-hop (`category: 1`)**:

```json
{
  "question": "Where did Caroline move from 4 years ago?",
  "answer": "Sweden",
  "category": 1,
  "evidence": ["D3:13", "D4:3"]
}
```

Neither cited turn answers the question alone: D3:13 — Caroline: *"...I've known these friends
for 4 years, since I moved from my home country..."* — establishes the "4 years ago, moved from
home country" fact but never names the country. D4:3 — Caroline: *"...a gift from my grandma in
my home country, Sweden..."* — names the country but says nothing about moving or timing. The
answer "Sweden" only follows from combining both, satisfying the
[Relational Integration definition's](../capabilities/02-relational-integration.md) (Capability
2) requirement that each cited fact contribute a piece the other doesn't.

**Temporal reasoning (`category: 2`)**:

```json
{
  "question": "When did Caroline go to the LGBTQ support group?",
  "answer": "7 May 2023",
  "category": 2,
  "evidence": ["D1:3"]
}
```

`evidence: ["D1:3"]` points to one turn — Caroline: *"I went to a LGBTQ support group yesterday
and it was so powerful."* — session 1 is timestamped "1:56 pm on 8 May, 2023" in the
conversation metadata, so answering requires resolving "yesterday" against that session date
(8 May − 1 day = 7 May 2023), not reciting a verbatim timestamp — consistent with the
[Temporal Reasoning definition](../capabilities/03-temporal-reasoning.md) (Capability 3).

**Adversarial (`category: 5`)**:

```json
{
  "question": "What did Caroline realize after her charity race?",
  "answer": null,
  "adversarial_answer": "self-care is important",
  "evidence": ["D2:3"]
}
```

`evidence: ["D2:3"]` points to one turn — Melanie: *"...I'm starting to realize that self-care
is really important..."* — the realization was Melanie's, about Melanie's own charity race, not
Caroline's. The question swaps the subject to trick the system into attributing someone else's
statement to Caroline; `adversarial_answer` records the wrong answer a system would give if
fooled, while the real gold `answer` is `null`, consistent with the
[Memory Calibration definition](../capabilities/10-memory-calibration.md) (Capability 10):
correctly recognizing the question as unanswerable given what was actually said.

## Capability scoring

Capabilities refer to [`../capabilities.md`](../capabilities.md) (14-capability taxonomy index;
see [`../capabilities/`](../capabilities/) for each capability's full specification), scored
against the Coverage rubric's Leg-A-gated decision rule: Leg A (authored targeting) is checked
first — if it fails, the verdict is ❌ **None** regardless of any byproduct examples; if it
holds, Legs B (concrete example) and C (metric isolation) decide between ✅ **Full** (both hold)
and 🟡 **Partial** (either falls short). All 14 capabilities are scored below — each capability
page already carries a full definition and boundary rules (per the current taxonomy), so a ❌
verdict here reflects a checked absence of authored targeting, not an unscored placeholder; it
is still "no guessing," per this project's methodology, because every verdict below is backed by
a checked primary source, not an assumed high-level impression.

This page covers the **question-answering (QA) task** in depth (Metadata through Sample data
above); the paper's other two tasks — event summarization (§4.2, evaluated with FactScore
precision/recall against the annotated `event_summary` field) and multimodal dialogue
generation (§4.3, evaluated with MMRelevance) — were checked only for capability-scoring
purposes below, not documented to the same depth (no dedicated sample data / task-format
section here yet).

- **Second annotation discrepancy found (unresolved)**: the `category: 2` (temporal) item
  `"When did Melanie run a charity race?"` → `"The sunday before 25 May 2023"` (evidence
  `["D2:1"]`) is answered from a turn stating the race was "last Saturday," in a session
  timestamped 25 May 2023 (a Thursday). "Last Saturday" relative to that date is 20 May 2023 (a
  Saturday); the gold answer names 21 May 2023 (a Sunday) instead — a one-day mismatch between
  the dialogue text and the annotated gold answer. Not used as this page's Capability 3 example
  for that reason; the LGBTQ-support-group example above was verified consistent instead.
- **BLIP vs. BLIP-2 discrepancy (unresolved)**: the paper's §5 states images are replaced with
  "captions generated using BLIP-2" for the QA/event-summarization tasks, while the repo's
  `README.MD` documents the `blip_caption` field as generated by the original
  `Salesforce/blip-image-captioning-large` model (BLIP, not BLIP-2). Both are official sources;
  neither has been used to override the other here. Does not affect QA-task scoring above, since
  captions (whichever model produced them) are only metadata on image-sharing turns, not part of
  the evidence used in the sample data above.
- **Annotation-label noise found**: at least one `category: 1` (multi-hop) item —
  `"What did Caroline research?"` / `"Adoption agencies"`, evidence `["D2:8"]` — has only a
  single evidence turn that alone fully answers the question, i.e. it reads as single-hop
  despite its label. This looks like isolated annotation noise (269/282 = 95.4% of category-1
  items do have genuine multi-session evidence) rather than a systematic mislabeling, but it's
  worth keeping in mind when auto-scoring by category alone — spot-check examples individually
  rather than trusting the label at face value.
- **Adversarial metric blind spot**: per the Metric section above, category 5 only credits
  exact substrings `"no information available"` / `"not mentioned"` — relevant to keep in mind
  when Capability 10 (Memory Calibration) is eventually scored against this benchmark.
